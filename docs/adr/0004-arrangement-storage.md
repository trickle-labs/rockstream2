# ADR 0004: immutable delta traces with per-domain SlateDB working indexes and bounded overlays

**Status:** Proposed storage candidate; G0.2 selects one layout using the neutral rubric in [ADR 0013](0013-minimum-mechanisms-and-independent-qualification.md). **Date:** 2026-11-26. **Owners:** storage and engine roles. Gate placement is refined by [ADR 0012](0012-staged-mechanism-adoption.md).

## Decision

Keep one authoritative metadata manifest and explicit durable history/recovery contracts. The following hybrid is the current candidate, not a preselected winner. G0.2 compares it with pure SlateDB history under common correctness, retained-cut, resource, recovery, SLO and cost limits. Select the simplest complete passing implementation, accounting for lifetime protocol, verification and operational cost; a simpler candidate need not beat the hybrid on every metric. Update this ADR and the owning spec with measured selection evidence before G2.

**Hybrid candidate:** separate **authoritative durable history** from **indexed working state** as follows:

1. **Authoritative Input & Delta Traces (Immutable Object Segments):** Accepted input transactions and committed per-interval operator/output deltas are written as immutable weighted Arrow/batch objects on object storage and selected by the committed manifest. Because staged segments are immutable and unreferenced until publication CAS succeeds:
   - Abandoned preparations require **zero database cloning** and **zero LSM attempt-namespace key filtering**; they are simply unreferenced objects reaped by GC.
   - Sequential scans, replay, historical delta delivery, and subscriptions read immutable segments directly without LSM compaction overhead.
2. **Indexed Working State (SlateDB + Bounded In-Memory Delta Overlay):** Use **SlateDB** for persistent point probes, join lookups, current-state serving indexes, and (when direct SQL `UPDATE`/`DELETE` is enabled) the explicitly budgeted primary-key image index, paired with an explicit **bounded in-memory indexed overlay** for trailing deltas between periodic SlateDB checkpoints (`Cp_ckpt <= Cp`):
   - **Tentative writes never pollute SlateDB:** During an unpublished interval, maintenance holds tentative updates in a local in-memory overlay, uploads immutable delta segments, and applies committed deltas into SlateDB *only after* publication CAS succeeds. On abort/CAS conflict, discarding the in-memory overlay costs zero SlateDB reopens.
   - **Checkpoint registration, writable crash recovery, and overlay bounds:** Taking a new non-expiring SlateDB checkpoint at a committed interval boundary `ckpt_cut <= Cp` must be durably registered in the metadata root (`(slatedb_instance_id, checkpoint_id, ckpt_cut)`) before trimming in-memory overlay entries `<= ckpt_cut` or retiring the prior checkpoint. If the trailing overlay hits its byte/count cap while checkpointing is pending or failing, maintenance applies hard admission backpressure (`RS_RESOURCE_LIMIT` or bounded wait) rather than growing unboundedly in RAM or evicting uncheckpointed deltas. On crash recovery, normal intervals that apply in one atomic SlateDB `WriteBatch` record `_meta/applied_cut = U` alongside committed mutations so clean reopen verifies `Cp_ckpt <= live_applied_cut <= Cp` and replays only `(live_applied_cut, Cp]` (zero double-apply); for chunked intervals, ownership takeover, or inconsistent `_meta/applied_cut`, recovery creates a **takeover-only** SlateDB clone (or fresh generation-scoped prefix) from the immutable manifest-referenced `Cp_ckpt` and replays `(Cp_ckpt, Cp]` cleanly—preserving zero per-interval clones on the hot path.
   - **Fast serving between checkpoints & historical lookups in `[S_hot, Cp]`:** Profiles without G3b-I retain latest, pinned and a bounded recent set of published versions and serve published interval-boundary cuts. At G3b-I, arbitrary-cut historical point lookups at `C ∈ [S_hot, Cp]` open the nearest preceding retained checkpoint `Cp_ckpt(C) <= C` and overlay `(Cp_ckpt(C), C]`—no LSM multi-version explosion and no undo deltas.
   - **Uniform Direct-DML PK image index:** Keyed direct-DML tables use this exact same SlateDB checkpoint + bounded input-log overlay, metadata checkpoint registration, `_meta/applied_cut`/takeover-clone recovery, and overlay-cap backpressure pattern (eliminating synchronous two-store atomicity between SlateDB and the metadata root).
   - **Per-domain isolation first:** Start in G0–G2 with **one SlateDB instance per result publication group (or partition)**—plus one for the ingestion domain's PK index when keyed direct DML is enabled—to preserve domain and quarantine independence ([ADR 0002](0002-consistency-domains.md)). G0.2/G3b measures idle object-store WAL/manifest cost per SlateDB instance so multi-domain physical grouping (with fenced writer ownership) activates cleanly when instance counts exceed the measured threshold.
3. **One locked storage path after G0.2:** G0.2 runs a focused real-provider comparison between this **immutable-delta + SlateDB-index + bounded overlay** layout and a **pure SlateDB-history** layout on `W1-G` (write/request amplification, post-CAS/mid-apply `SIGKILL` writable reopen with zero double-apply, metadata checkpoint registration and overlay-cap backpressure, cold recovery, and one in-process historical lookup)—and locks **one** production layout before G2 under the [predeclared G0.2 rubric](../planning/qualification.md#g0-feasibility-decisions). Separate-process reads and grace-window deletion under live readers move to G4.0; Direct-DML PK-index recovery is accepted in P2.1.

The comparison must include equivalent publication/retry/recovery work, not unequal validation reads or subsets of payload bytes. If no candidate satisfies frozen limits, record fail/inconclusive and re-decide the scope; do not keep two production layouts. These decisions preserve all authority and pin/retirement invariants.

## Alternatives and consequences

- **Per-interval SlateDB shallow clones:** Rejected as the default microbatch staging mechanism; shallow clones copy referenced WAL SSTs and create manifest/external-checkpoint dependencies designed for occasional branching, not sub-second interval preparation (takeover-only clones are reserved strictly for crash/ownership recovery when chunked or dirty apply prevents clean `_meta/applied_cut` reopen).
- **LSM attempt-namespace key filtering inside SlateDB:** Rejected as unnecessary complexity when immutable delta segments + in-memory tentative overlays already isolate unpublished preparations outside the LSM tree.
- **Premature multi-domain SlateDB physical grouping:** Deferred until measured idle per-instance WAL/manifest overhead justifies fenced physical grouping.
- **Trade-off accepted:** Keeping SlateDB checkpoints amortized means maintenance and serving nodes must maintain a small bounded in-memory overlay `(Cp_ckpt, Cp]` and write both compact delta segments and post-commit SlateDB updates. G0.2 explicitly measures overlay memory, cold-start replay latency, and dual-write cost against pure SlateDB history.

## Gate

**G0.2** measures both layouts on one real provider with `W1-G` (amplification, post-CAS/mid-apply `SIGKILL` writable reopen with zero double-apply, metadata checkpoint registration and overlay-cap backpressure, cold recovery, and an in-process lookup at a retained earlier cut) and locks one storage design before G2 under the [predeclared G0.2 rubric](../planning/qualification.md#g0-feasibility-decisions). Direct-DML PK-index recovery is in P2.1; arbitrary-cut and real grace-window deletion evidence is collected at G3b-I/G4.0 respectively. [Consistency and storage](../design/consistency-and-storage.md) and [ADR 0009](0009-logical-mvcc.md) define the normative contract.
