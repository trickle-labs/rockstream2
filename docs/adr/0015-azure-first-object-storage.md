# ADR 0015: Azure-first object storage qualification

**Status:** Proposed for review, 2026-11-27, under [issue #36](https://github.com/trickle-labs/rockstream2/issues/36). Extends [ADR 0014](0014-incremental-delivery-and-earned-complexity.md); replaces AWS-specific first-provider assumptions in [ADR 0003](0003-publication-and-metadata.md) and the owning specification. No backend, layout, gate or cloud profile is qualified by this decision.

## Context and decision

AWS S3 access is not currently practical; the project owner confirms Azure Blob Storage access can be obtained. Select Azure Blob Storage as the first real provider for G0.2 and use [Pigsty Silo](https://github.com/pgsty/silo) as the local S3-compatible test service. Preserve one production runtime and one storage layout chosen on comparable real-provider evidence. AWS and other providers remain optional later qualifications, not initial dependencies or implied supported targets.

Use the existing narrow storage/root boundary and the pinned Rust `object_store` implementation shared with SlateDB where compatible. Its [conditional put modes](https://docs.rs/object_store/latest/object_store/enum.PutMode.html) and SlateDB's [Azure integration](https://slatedb.io/docs/tutorials/abs/) are evidence of available interfaces, not conformance of the future pinned build. No custom multi-cloud framework, Azure-specific coordination service or alternate authority protocol is needed. Test the actual client and dependency behavior rather than assuming API compatibility.

## Required object-store capability contract

- Strong, linearizable reads of the authoritative current root at a known key without listing; complete immutable data/manifest writes are readable before publication.
- Atomic create-if-absent and conditional replacement against an opaque expected-version token. Azure's [concurrency contract](https://learn.microsoft.com/en-us/azure/storage/blobs/concurrency-manage) and [conditional headers](https://learn.microsoft.com/en-us/rest/api/storageservices/specifying-conditional-headers-for-blob-service-operations) describe `If-None-Match: *` and `If-Match` using ETags. Use `PutMode::Create` and `PutMode::Update` where the actual adapter satisfies the contract; never fall back to unconditional replacement. ETags are opaque, not content hashes or ordered epochs.
- Correctly distinguish definitive conflicts from ambiguous outcomes (including timeouts, lost success responses, throttling, and SDK retries); reconcile ambiguity using stable operation identity and durable outcomes even after later root advancement. A failed retry is not proof that the original write failed. Preserve stale-owner fencing, publication dependency closure, GC protection and every existing invariant.
- Durability for the explicitly selected failure envelope; bounded retries/backpressure on provider or network faults. Measure provider-specific error mappings, request and byte amplification, retained versions, cleanup and pricing. Do not rely on provider lifecycle deletion of protected objects.

Propose a disposable Standard GPv2 Hot block-blob account/container with zone-redundant storage (ZRS) in one region, using the primary endpoint. [Azure redundancy documentation](https://learn.microsoft.com/en-us/azure/storage/common/storage-redundancy) describes synchronous multi-zone ZRS replication. Freeze the actual region, SKU, redundancy, client/runner placement, account/container lifecycle/versioning settings, and numeric budgets before confirmatory runs. A locally redundant or single-zone tier can be a diagnostic or separately named weaker profile; it cannot qualify the default zone-loss envelope. Asynchronous secondary-region reads are not authoritative current-root reads; cross-region DR retains its separate RPO/RTO, fencing and restore requirements.

## Local versus real-cloud evidence

Silo is for local development, CI and bounded fault/latency injection. Run the same logical conformance and crash harness on it and on Azure with isolated datasets. Pin the Silo image/version; record actual fault delivery, seed/configuration, request/byte counters and any differences in adapter behavior. Silo is a real local object server, not a replica of Azure's regional service. Artificial delay and local request counts support debugging, sensitivity analysis and provisional estimates, not cloud latency, durability or billed cost claims.

While obtaining scoped access, continue G1 when its own foundation prerequisites pass and extend disposable G0.2 probes, including equivalent candidate representations, negative controls and crash/recovery tests. Do not lock a layout, merge dependent G2 implementation or qualify a cloud profile using local evidence alone. On real Azure, complete the full G0.2 rubric: serialized one-operation-per-CAS metadata baseline, conditional create/update and lost-response reconciliation, sequential round trips, exact equivalent candidate work and complete costs, bounded overlays/trailing state, post-publication and mid-apply process kill/reopen, retained-cut lookup, and cold recovery. Batching/paging still require ADR 0014's measured triggers. Record real request charges and relevant compute/network/retained-state cost under the chosen pricing configuration; preserve inconclusive runs.

Before execution supply a named disposable resource/container, temporary least-privilege credentials via a trusted environment, explicit spend/time limits, workload/size limits and cleanup ownership. Never put credentials in the repository, issue, PR or logs; no production resources or privileged operations. The owner has confirmed availability, not provisioned access or spend authorization. G0.2 remains blocked for real-cloud runs until the resource, scoped access and budgets exist; the existing [issue #16](https://github.com/trickle-labs/rockstream2/issues/16) and [local probe PR #18](https://github.com/trickle-labs/rockstream2/pull/18) remain the implementation/evidence lane.

## Consequences and qualification

Use Silo to shorten the feedback loop, Azure to establish reality, and one provider-independent logical contract. Existing S3-motivated latency numbers are retained as unmeasured comparison targets, not estimates or promises for Azure. The selected Azure configuration must independently pass conformance, layout selection and subsequent applicable G2/G6 safety, recovery, security, physical resource, operational and economic gates. A provider failure or inconclusive experiment blocks the affected decision; revise the configuration/workload or choose another provider explicitly, never weaken the contract. Qualify S3 or another provider only when a workload requires it and the same applicable contract and provider-specific evidence exist.
