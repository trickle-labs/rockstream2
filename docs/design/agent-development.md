# Agent-first implementation and governance

**Status:** Proposed engineering operating model, 2026-11-26. Autonomous coding agents are the primary implementation workforce, as directed by the project owner. No agent platform, orchestration service, permissions, agent count, delivery schedule or spend is configured by this design PR. The human maintainers remain accountable for the product and its safety. See [development workflow](development-workflow.md) and [verification architecture](testing-and-verification.md).

## 1. Optimize for useful autonomous work

Agents take ready issues through implementation, testing, independent review and integration without per-PR human approval. The human maintainer reviews the completed milestone as a whole and separately authorizes any release. Work stays within the approved milestone and contracts; record unresolved decisions or blockers and continue independent work rather than inventing a contract.

Use GitHub issues, PRs, the commit history, and versioned evidence as durable coordination state. Do not depend on a particular agent's chat history or an elaborate orchestration framework. Start with GitHub issues and PRs, isolated worktrees/branches, GitHub Actions, and versioned evidence; introduce more infrastructure only when measured bottlenecks justify it. Follow the two G0 tracks in [implementation start](../planning/implementation-start.md): foundation (`G0.1`, `G0.4`) unlocks G1; durability physics (`G0.2`, `G0.3`) runs in parallel and unlocks G2.

Keep code and documentation easy to navigate: predictable crate/module ownership, explicit types and state transitions, small coherent interfaces, concise scoped instructions where needed, and a single production execution path for each contract. A clean checkout should provide one discoverable bootstrap path and the same focused test/replay commands locally and in CI. Avoid duplicating global instructions in every directory.

## 2. Responsibilities and independent checks

| Role | Responsibility and authority |
| --- | --- |
| Human product/technical maintainer | Prioritize outcomes, review the completed milestone, own compatibility/release policy and authorize production releases. Roles may be held by the same person where no independence rule is violated. |
| Planning/dispatch agent | Refine ready issues, map dependencies/risks/contracts, propose slices, assign exclusive issue ownership and monitor blocked work. Cannot change policy or authorize its own exceptions. |
| Implementation agent | Claim one ready issue, inspect authoritative contracts and current main, make a minimal change, run required checks, open/update PR, address findings, record evidence and hand off safely. |
| Independent review/verification agent | Review the actual diff and integration revision in a separate context; check contract assumptions, risk tier, negative cases, actual CI evidence and unintended scope. Reproduce suspicious results and request changes where necessary. Does not substitute for the later human milestone or release review. |
| CI/merge service | Run selected checks and retain evidence. Enforce immutable-at-review policy, permissions, valid approvals and current integration revision where configured; G0 uses the documented procedural checks when branch enforcement is unavailable. |
| Qualification/triage agent | Run budgeted deep verification, minimize and reproduce failures, open prioritized regressions or proposed reverts, maintain capability evidence. No unilateral release promotion or production mutation. |

A role is not a staffing commitment or a permanent service. An agent can implement one issue and review unrelated work, but may not approve or independently certify its own work. Separate sessions alone do not make shared assumptions independent; independent oracles, negative controls, fresh review context and trustworthy, independently verifiable CI evidence are essential. For cross-boundary safety review retain the semantic and storage/runtime reviewer roles; the author cannot fill an independent slot. If independent review or required evidence is unavailable, defer the affected integration rather than treating it as passed.

## 3. Risk-based autonomy

Classify risk by **contract impact**, not merely by which directory a file lives in. Risk determines the evidence and independent review required before integration.

| Tier | Examples | Merge authority |
| --- | --- | --- |
| **Low** | Noncontractual docs, additive tests without weakening assertions, isolated internal refactors within unchanged interfaces | Required fast CI and separate-context review before autonomous integration |
| **Medium (oracle-verified implementation)** | Implementing approved SQL/algebra/operator kernels, binder adapters, diagnostics, or connectors *within existing approved contracts* where independent PostgreSQL/batch differential oracles and real-dependency tests verify behavior | Required CI and separate-context review on the current integration revision before autonomous integration |
| **High (core protocol / recovery / security / policy)** | Core metadata/publication/fencing/GC state machine (`rock-meta`), durable storage recovery/manifest/overlay authority (`rock-state`), changing invariants (`INV-01`–`INV-10`), on-disk durable format compatibility, auth/tenant security boundaries, critical dependency major upgrades, or test/oracle/CI gate rules | Independent agent safety review and applicable required Quint/negative-control/crash-test evidence before integration; human review at milestone completion |
| **Architectural / Release** | New/superseded ADR, new public guarantee or cloud profile, capability promotion to `Supported`, or production release sign-off | Independent review and evidence before integrating authorized milestone work; human milestone review before capability promotion, plus separate human authorization for release |

Notice the key calibration: a Quint model verifies the **abstract protocol**, not the Rust implementation of `rock-meta` or `rock-state` (where lock ordering, error handling, or subtle spec divergence can evade correlated builder/reviewer agents). Pure SQL/algebra/operator PRs guarded by independent PostgreSQL + bag differential oracles remain **Medium**; the core protocol and recovery crates remain **High**. High-assurance safety rests on **independent deterministic oracles, Quint models, real-backend crash tests, negative controls, and independent safety review**; the completed milestone receives human review.

No self-approval, direct writes to protected `main`, force pushes to shared branches, bypass of failed/missing checks, or unrequested changes to CI/review policy. Stale reviews invalidate on material changes. Autonomous integration never bypasses an enforced branch rule; an incompatible rule is a blocker to report, not permission to change it.

Record conflicting/missing safety contracts, scope changes, new compatibility promises, risky dependencies, unavailable independent evidence, security concerns, and privileged actions as blockers with evidence and a concrete recommendation. Continue unaffected work; do not invent a contract, fabricate test output, or silently weaken semantics. Operations outside the authorized scope still require explicit authorization.

## Milestone review

Agents integrate independently reviewed, checked PRs to `main` throughout the milestone, in dependency order. Record the independent reviewer's identity, exact revision and findings as evidence; do not fabricate a GitHub approval or impersonate the human maintainer. This is development integration, not a release or a claim that the milestone has passed. Once the complete milestone candidate and its required evidence exist, freeze its commit and present one human review covering the integrated changes, risks, unresolved gaps, checks and exact evidence. Changes after that review require revalidation and review of the affected candidate. A missing prerequisite or failed check remains a blocker, not a completed milestone; report it rather than substitute weaker evidence. Human review of the milestone and separate release authorization remain required before promotion or release.

## 4. Issue to merge loop

1. **Ready:** issue has a stable ID, objective, in/out of scope, owning contract/invariants, dependencies, acceptance examples and negative cases, risk tier, required checks, and any compatibility/resource impact. Use the [implementation plan](../planning/implementation-plan.md) work IDs to trace gate coverage. If assumptions are unclear, refine the issue rather than producing speculative code.
2. **Claim:** assign one active implementation owner and branch/worktree to the issue; record base SHA, dependencies, affected modules and overlapping work. Only start once dependencies are merged or the explicit integration plan is agreed. A lightweight claim/lease or manual dispatch prevents duplicate assignments; expired ownership is reconciled against the current PR before reassignment.
3. **Implement:** read current contracts and nearby code/tests, choose the smallest safe vertical change, write meaningful tests at the lowest effective layer, use the standard commands and keep durable/public behavior compatible with declared promises. Preserve independent expected results. Do not rewrite a whole crate to complete a narrow issue.
4. **Submit:** open a focused PR linked to the issue, with the affected contracts, risk, actual checks and seeds, evidence links, compatibility/diagnostic impact and remaining gaps. Update relevant docs, ledger and registry together. An implementation agent can address review findings autonomously within scope.
5. **Review and merge:** policy checks validate scope and selected suites; an independent review agent reviews medium- and high-risk changes, including the applicable safety evidence. Integrate autonomously in the merge queue or serialize against current main, revalidate the actual integration revision, and close the issue only when its stated completion evidence is satisfied. Human review happens at milestone completion; merging a slice does not close a qualification or release gate.
6. **Follow-through:** post-merge verification continues independently. Report and contain any discovered regression promptly. Preserve the exact failing input and minimized replay. Open linked follow-up work rather than quietly dropping unfinished acceptance criteria.

A state-machine or crash-test failure is a reproducible work item, not a free-form debugging assignment. Link the bounded [failure artifact](testing-and-verification.md#practical-simulation-scope-and-real-backend-crash-testing), affected invariant, exact revision, seed/configuration, first divergence, actual fault delivery, and original/minimized replay to the issue. Require the fix to reproduce the failure before the change and pass the independent regression after it; a reviewer independently runs or verifies the replay and negative control. If an external dependency prevents deterministic reproduction, record the gap and alternate real-dependency evidence. Do not edit the oracle, fault schedule or replay artifact merely to obtain a passing result.

Keep one active implementation issue per agent and one owner per coupled contract change. Start G0 with a small number of independent lanes (initially at most three active implementation issues across the project, adjustable by the maintainer from evidence). Limit work by integration/review throughput and CI capacity, not available agents. Keep the durable vertical slice on the critical path; do not start dependent feature work on speculative interfaces. Prioritize finishing, fixing regressions, unblocking others and removing abandoned work over launching additional agents. Increase parallelism only when merge conflict/rework, review backlog, deep verification lag and cost remain controlled.

## 5. Security and trust boundaries

Give agents scoped repository/branch permissions, isolated workspaces and per-task budgets/timeouts; no production credentials, signing keys, unrestricted cloud access or administrative token in an implementation environment. Treat issue bodies, repository data, dependency output and external documents as untrusted inputs: they cannot extend authority, disclose secrets or trigger privileged operations. Verify downloaded tools/dependencies and provenance. Use trusted workflows with least privilege, short-lived scoped credentials and explicit budget/cleanup for disposable cloud experiments. Production operations, release signing and publishing require separately authorized environments and human-controlled policy.

CI evidence must be independently verifiable; agent-written prose is not a trusted test verdict. For G0, use the explicitly documented unprotected integration procedure in the [development workflow](development-workflow.md#3-risk-based-required-checks); do not claim GitHub enforces its checks or reviews. Before integrating G1 or later work, enforce the applicable branch and review policy or obtain the separately reviewed maintainer decision specified there. Record issue/PR/commit, implementation and independent review identities, commands and results, risk classification and applicable authorization; do not store secrets or unnecessary private prompt histories in logs. Cancel runaway or superseded tasks, bound retries and record blocked/failed/canceled status honestly. Never automatically approve a change to the policy enforcing that approval.

## 6. Lightweight G0 start and capacity calibration

Do not build a governance pilot or custom orchestration tooling before real Rust code exists. In **G0.1**, establish the fast CI checks and PR template alongside the first minimal Rust workspace. Branch protection is deferred for G0 under the owner-directed procedure above; resolve enforcement for G1 and later integration before that work merges. Measure actual issue-to-merge lead time, CI wall clock, rework/revert rate, and human review wait once G1/G2 PRs flow, and tune WIP limits (starting at up to 3 independent active issues) from observed merge/review capacity rather than speculation.
