# Rockstream implementation experience report

**Date:** 2026-11-26  
**Status:** retrospective and recommendations for review; not a new architectural decision or qualification sign-off.  
**Reviewed baseline:** [Rockstream main at f550c8f00949](https://github.com/trickle-labs/rockstream/commit/f550c8f0094903d8989447ec09dfc3859d168938); [Rockstream 2 main at ba8915213df1](https://github.com/trickle-labs/rockstream2/commit/ba8915213df114572921fb046caa3e135f21dd10).

## Executive summary

Rockstream demonstrated that a small project can build a remarkably broad streaming database using a Rust workspace, domain-specific invariants, property and oracle tests, simulation, formal methods, reproducible evidence and rapid iteration. Its most valuable inheritance is not the entire implementation: it is the accumulated knowledge of how incremental computation, persistent state, distributed authority, and public SQL/connector contracts fail.

The main process failure was a mismatch between **feature progress and evidence of integrated behavior**. Implemented mechanisms, named tests, model checks, synthetic qualification records and milestone sign-offs sometimes stood in for the much stronger claim that the ordinary executable behaved correctly under the stated conditions. Repairing that mismatch required substantial late work. As that work strengthened assurance, CI grew into a throughput bottleneck. There were also unnecessary compatibility commitments, duplicated documentation, and late discoveries of architectural and algorithmic performance ceilings.

This is not an argument for fewer correctness checks. It is an argument for fewer simultaneous product promises, earlier proof of the complete path, independent evidence, and much cheaper feedback per safe change.

**For Rockstream 2:**

1. Start with one exceptional user journey and one durable, executable vertical slice; let every gate extend that same slice. No unsupported mechanism is a completed capability.
2. Inherit counterexamples, invariant meanings, replayable inputs, real-process scenarios, and independently checked results before inheriting code. Make every donor decision explicit.
3. Build evidence infrastructure and a small, reliable CI gate before feature velocity grows. Prove that the tests really execute and fail for relevant defects. Separate merge, integration, and capability-promotion evidence.
4. Treat algorithmic work, whole-process resource bounds, storage/coordination latency, and operating economics as first-order requirements measured on the intended path, not as optimizations to postpone.
5. Keep agent concurrency bounded by integration, independent review and verification throughput. Optimize accepted safe changes, not generated code, milestone count, or passing test count.

Most of these lessons are already embodied in the Rockstream 2 design. The recommendations below make them concrete at the existing G0–G6 gates; they do not propose a parallel roadmap or a second qualification framework.

## 1. Method and limits

This review complements the [current-system audit](current-system-audit.md), which maps the existing architecture and capabilities. The present report asks how the implementation and delivery process evolved, what evidence became trustworthy, what rework occurred, and what to carry forward.

Evidence examined: the pinned main tree and selected implementation entry points; the GitHub PR collection (all four pages, 357 distinct returned PRs); selected early, middle and recent main-history commits; plans, sign-offs, audit reports, acceptance issues, targeted PR descriptions and selected discussions; and GitHub Actions metadata for representative historical runs. The old repository contains 2,293 blob entries at the pinned tree (including fixtures, documentation, generated files and evidence, not a source-LOC count), with 17 Rust crate directories, 292 entries under .claude, and 179 under sign-offs. These counts describe the repository footprint, not implementation quality or agent effort.

Evidence categories used here:

- **Observed:** source/tree, PR state or Actions metadata read through GitHub. A merged PR establishes a change was integrated, not that every claim in its description is true.
- **Reported:** a historical audit, PR test result, measurement or sign-off; attributed to its authoring artifact and scoped to that revision and profile. Selected run identities and conclusions were independently checked in Actions metadata; underlying logs/artifacts were not all downloaded.
- **Inference / recommendation:** what the observed history suggests. It is not a claim about individual contributors, private decisions, agent behavior or customer incidents.

No checkout, build, tests, proof checker, fuzz campaign, benchmark or cloud deployment was independently run for this retrospective. It is not an exhaustive source or security audit. Some large files and historical discussions were not available in full. There is no reliable time/effort, agent-token/cost, customer adoption, production-incident or utilization dataset here. PRs are not units of effort; direct commits are not counted as PRs. No causal agent-productivity claim is possible. The dates below refer to the events or historical evidence, not a claim that all older defects persist at main.

## 3. What worked well — preserve deliberately

### 3.1. Correctness starts with domain semantics

Z-set weights, explicit merge laws, checked arithmetic, logical cuts, typed errors and reproducible histories gave the project a shared vocabulary for correctness. The early law harness in [#8](https://github.com/trickle-labs/rockstream/pull/8) covered associativity, commutativity, identity, serialization and malformed inputs. Specialized operator and batch-reference infrastructure accumulated through [#29](https://github.com/trickle-labs/rockstream/pull/29). This is a much stronger starting point than example-only SQL testing.

A particularly useful later refinement is the [join oracle mutation pilot](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/docs/testing/join-oracle-mutation-pilot.md). A six-epoch weighted history exercises both prior-state join terms, simultaneous deltas, deletions and reinsertion. Its complete typed bags at each cut detect five deliberately introduced faults, including dropping a negative delta and losing a multiplicity product. The pilot reports exact expected and actual rows, distinguishes existing coverage from new coverage, and does not extrapolate a general mutation score.

**Transfer:** preserve the histories, laws and expected output semantics in P0.1/G1. Keep the semantic kernel small enough to test without cloud, SQL server or a distributed topology. Use typed complete multisets, not counts, sets or final checksums alone. Expected results must not reuse the candidate's incremental lowering or operator logic. Test each promised cut; final-state equality can hide transient incorrect publications.

### 3.2. Layered verification is valuable when its boundaries are explicit

FizzBee models, Verus production-kernel contracts, deterministic simulation, real backends and fuzzing cover different failure classes. [ADR 0006](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/docs/adr/0006-persistence-replay-compaction.md) distinguishes persistence-kernel proof obligations from storage internals, cross-process fencing and distributed liveness. [#84](https://github.com/trickle-labs/rockstream/pull/84) maps acceptance obligations to authority, identity, and durable progress boundaries. This is valuable because failures in these boundaries cannot be covered adequately by happy-path functional tests alone.

The project also learned to verify the verifier: [#234](https://github.com/trickle-labs/rockstream/issues/234) found constant-false proof fixtures that did not exercise the production guard they purported to protect. [#252](https://github.com/trickle-labs/rockstream/pull/252) reports that six production-source mutants were rejected with both baselines verified and the logs retained. That is a stronger form of assurance than a check demonstrating only that the prover rejects an obviously false assertion.

**Transfer:** reuse obligations and proof techniques, not a claim that old proofs cover a new protocol. For each model, name production transitions, exclusions and boundary tests. In P0.9 prove the oracle, fault injector, and evidence gate reject known violations; for a high-risk change require a relevant counterexample rather than ceremonial edits to unrelated model files.

### 3.3. The independent audit and corrective loop paid off

The Sept 21 audit identified actual reproducible bugs in catalog retry deduplication and workload identity recovery as well as weaker checks. It classified executed failures, source-confirmed gaps and unexecuted defect candidates separately. [#101](https://github.com/trickle-labs/rockstream/issues/101) turned one reproduction into precise acceptance criteria; [#142](https://github.com/trickle-labs/rockstream/pull/142) reports failing-before/passing-after evidence and explicitly discloses a new snapshot compatibility boundary. [#149](https://github.com/trickle-labs/rockstream/pull/149) addresses stable workload IDs and [#150](https://github.com/trickle-labs/rockstream/pull/150) addresses incomplete durable catalog history.

This is the strongest development pattern to institutionalize: inspect the actual path, reproduce the defect, freeze its acceptance contract, make a bounded change, independently check the regression, record remaining limitations, and preserve the case.

**Transfer:** independent investigation should be routine, not a late cleanup campaign. Adopt a small weekly rotation of adversarial contract review and simplification within the existing agent operating model; triage findings by real impact, minimize reproductions and attach them to existing work IDs. An open [software-farm design PR #448](https://github.com/trickle-labs/rockstream/pull/448) proposes Hunter and Gardener roles; borrow its learning/curation intent, not an unproven orchestration platform. No defect or PR quotas, and no autonomous authority to weaken guarantees.

### 3.4. Pragmatism and honest qualification can coexist

The project was willing to remove real scope. The August [focus amendment](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/ROCKSTREAM_PROJECT_FOCUS.md) removed extra external connector families rather than maintaining a permanent compatibility, CI, security and recovery burden. PostgreSQL wire and internal object storage remained essential. The October 19 [#132 scope override](https://github.com/trickle-labs/rockstream/issues/132) narrowed the v0.72 shipping gate to practical resource, scheduling, authorization, subscription and recovery behavior, retired benchmark-only requirements, and explicitly forbade claims of unmeasured p99, capacity or economics.

The [v0.72 sign-off](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/sign-offs/v0.72.md) identifies candidate 5c2e73f0e6b9d787c91adf388d4c8f06688f918d and reports 17/17 hosted smoke cases, 21/21 real-cluster chaos scenarios, and seven decoder fuzz targets. For this report, Actions metadata confirmed that [normal CI](https://github.com/trickle-labs/rockstream/actions/runs/40302807525), [smoke](https://github.com/trickle-labs/rockstream/actions/runs/40310837260), [chaos](https://github.com/trickle-labs/rockstream/actions/runs/40310738691) and [fuzz](https://github.com/trickle-labs/rockstream/actions/runs/40310723666) each report success for that exact implementation SHA. Counts and coverage interpretation remain sign-off-reported, not independently rerun. The final integrated commit and authorized tag are separate requirements; this does not establish a signed release.

The [v0.73 ledger](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/sign-offs/v0.73.md) is another useful example: partial slice results are recorded, but all integrated exit criteria are still unchecked and no complete candidate is signed off.

**Transfer:** deliberately define the smallest useful supported surface. Allow a maintainer to defer optional qualification scope with an explicit rationale and revised claim. Never relax core correctness, durability, security or isolation to meet a date. An unexecuted experiment remains unmeasured; merged slices do not automatically qualify an assembled candidate.

## 4. What did not work — root causes and concrete alternatives

### 4.1. Milestone sign-off got ahead of the evidence

The historical [v0.59 assessment](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/recommended-next-steps-after-v59.md) describes a sign-off roughly 57 minutes after the prior implementation landed, despite a stated 14-day frozen-candidate soak with reset on change. It also records version/tag/provenance inconsistencies at that time. These are historical findings, not assertions about present-day branch protection. The problem is structural: a human-readable checklist can assert a long-running, physical, or independently reviewed outcome without any machine-enforced link to the thing that actually ran.

A second example: the Sept audit inventoried 3,932 ordinary test attributes, 23 property-test blocks and 542 integration-test targets, but identified 49 of 67 simulation integration targets with no workflow invocation. Those counts were static inventory at v0.68; neither the count nor the green CI then was complete evidence. [#110](https://github.com/trickle-labs/rockstream/issues/110) / [#157](https://github.com/trickle-labs/rockstream/pull/157) subsequently addressed ownership and execution accounting, including negative controls for zero selection, skips, missing features/services and missing terminal results.

**Root cause inference:** progress was tracked largely in terms of version/feature and artifact completion before execution provenance was a hard prerequisite. Large plans and checklists made reviewing the relation between each promise and its evidence increasingly expensive.

**Better approach:** use one machine-readable capability/invariant ledger with a simple explicit state transition: specified → implemented (not necessarily reachable) → integrated/verified for an identified profile → qualified for promotion. Unsupported/retired, blocked, and incomplete must be expressible. Bind a gate to source and binary identity, toolchain/lock, feature/profile/backend, required cases, actual outcomes, independent checker version, evidence digests, limitations and expiry/invalidations. A build artifact, skipped test, stale green run or generated sign-off is not promotion evidence. Make this a minimal extension of P0.9 and qualification, not another huge reporting system.

### 4.2. Self-confirming tests hid gaps

The [test-suite audit](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/docs/test-suite-audit-2026-09-21.md) describes chaos tests manufacturing recovery observations, operators tested via the wrong implementation, and simulated suites not executed in CI. [#185](https://github.com/trickle-labs/rockstream/pull/185) gives a concrete correction: a Docker chaos test had copied input rows into its output oracle and treated Docker command duration as recovery. Its replacement ran production source, lease client, compiled view and transactional Kafka exporter using separate worker processes, Kafka and MinIO, killed an owner with durable work pending, and observed the actual view, output records, offsets, fencing and complete typed history. The PR reports one correct-query recovery observation at 44,824 ms, and negative controls for corrupt values, duplicates, suppressed progress and missed deadlines; one sample is not a percentile.

Similarly, [#405](https://github.com/trickle-labs/rockstream/issues/405) documents synthetic 1/2/4/8-worker qualification values presented as scaling tests. The pinned [horizontal scale tests](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/crates/rockstream-runtime/tests/horizontal_scale_qualification_tests.rs#L10-L39) still construct sample_reference_run fixtures; later tests include rejection of synthetic fixtures as release evidence. Such fixtures are legitimate *checker unit tests*, never measurements. [#413](https://github.com/trickle-labs/rockstream/pull/413) introduced an independent scale qualification program; a merged harness is not a completed scale campaign.

**Root cause inference:** the output of a test infrastructure component was confused with the observation that the infrastructure was intended to produce.

**Better approach:** in every end-to-end scenario, specify the observation boundary before writing the test. Capture real public-client results and independently observed side effects, actual fault delivery and timing from event-to-event (not harness command duration), including full bags/weights, source offsets, durable inventory, and sink transactions as applicable. Keep synthetic records conspicuously marked. Require negative controls for missing/malformed evidence, wrong values, duplicate/drop, stale-owner access, and faults that never fired. Use the same case data for simulation and real-process execution, but retain independent expected outputs. In G0, break at least one real invariant deliberately and show the gate catches it.

### 4.3. Useful algorithms and components were not always on the normal execution path

By November [#400](https://github.com/trickle-labs/rockstream/issues/400) reported that normal client/connector ingestion and reads still routed through ControlService JSON/TSV, CLI workers had unwired exchange inlets, SQL lowering did not invoke real distributed planning, and per-frame fencing required control round-trips. [#420](https://github.com/trickle-labs/rockstream/pull/420) reports wiring direct Arrow IPC, exchange inlets, ownership discovery and executable physical planning. This is not proof that the new distributed path has a qualified capacity envelope; it is a substantial integration fix.

Likewise, [#402](https://github.com/trickle-labs/rockstream/issues/402) identified factorized operators that cloned entire state, recomputed nested joins, and scanned/rewrote surviving keys, and an aggregate path not using available merge persistence. [#409](https://github.com/trickle-labs/rockstream/pull/409) reports changed-key indexes and transactional overlays, point writes, checked merge deltas and resource-budget changes. The problem was not a lack of advanced algorithm names; it was the gap between algebraic incrementalism and the actual physical work for a small update. [#407](https://github.com/trickle-labs/rockstream/issues/407) remains open on dependency-scoped progress and regional-cell qualification; the [current-system audit](current-system-audit.md) also records existing scope-aware frontier primitives, so the issue should be read as a wiring/qualification gap, not absence of all scoped progress code.

**Root cause inference:** horizontal implementation (operator, exchange, storage, frontend, control) enabled fast progress in each subsystem while making it easy to defer complete integration. Complexity goals were asserted before the actual work path had instrumentation.

**Better approach:** make W1-G traverse the same selected public API, planner, production operator, persistence and publication path from G2; extend to live sources/sharing in G3 and the same contract over workers in G4. Expose plan/operator IDs, selected strategy and counters through observable diagnostics; a type, interface, mock or loopback test cannot satisfy a physical-path requirement. Require work proportional to affected keys/results (allow explicitly documented unavoidable output amplification), measured at fixed delta size while unrelated retained state grows. Measure allocations/copies, scanned/read/written keys, bytes, I/O, queues and peak live memory, not only elapsed time. Distinguish whole-process RSS from individual operator reservations. Prove ordinary client data does not traverse an unintended coordination bottleneck.

### 4.4. Cross-boundary durability and authority bugs were expensive to discover late

Representative counterexamples are more instructive than generic architectural rules:

| Historical case | What went wrong and what changed | Successor obligation |

**Root cause inference:** durable correctness is not a property of a storage batch alone. Every authority/acknowledgement/visibility boundary must compose with retry, recovery, fencing, compaction, and the external system's real semantics.

**Better approach:** maintain a transition/fault ledger before implementation and bind tests to named fault sites: before and after acceptance, preparing durable state, publication, response, source ACK, sink delivery, pin acquire/release, reclaim, replacement and recovery. Enumerate which outcome is permissible at each fault, what identity is stable, and what independent evidence disambiguates unknown results. Start with deterministic schedules and targeted real-backend tests, including negative controls that prove the fault fired. Exercise actual reclamation; retaining everything can make safety tests pass while hiding leaks. Carry the cases above forward even when the architecture changes.

### 4.5. Product scope, documentation and code boundaries accumulated carrying cost

Connector breadth was not free, as the [focus amendment](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/ROCKSTREAM_PROJECT_FOCUS.md) explicitly acknowledges. The v0.59.13 sign-off invested in a generated product-surface manifest and drift/mutation checks. Yet the [Rockstream 2 current-system audit](current-system-audit.md) finds later disagreements between README, capability tiers, SQL reachability and Kafka delivery labels. A generated catalog is useful, but it does not by itself prove public-path support or keep all narrative copies consistent.

The pinned tree contains a gateway server source blob of 1,123,307 bytes, control service of 331,289 bytes, and catalog_stubs of 277,290 bytes (Git blob sizes). Size is not a defect or measure of cohesion; it is a signal to investigate. These large surfaces, the 17 crates, and the overlapping design/roadmap/plan/evidence documents create substantial review and context costs, especially for an agent that needs to locate the authoritative path. The historical repository's [AGENTS.md](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/AGENTS.md) explicitly emphasizes output/token economy, selective reading, test summaries and tooling wrappers. An open [#456](https://github.com/trickle-labs/rockstream/pull/456) proposes simplifying agent guidance/removing repo RTK setup. These observations do not establish measured token savings or whether the wrapper was beneficial.

**Better approach:** make canonical contracts short and indexed; let generated capability/error/reference surfaces derive from one owning declaration and cross-check actual behavior. Archive superseded plans instead of leaving competing normative copies. Prefer domain types and narrow dependencies (pure semantics independent of storage/network); separate orchestration, SQL protocol, catalog/metadata transition logic and backend adapters by responsibility, not arbitrary line limits. Treat every new dependency, feature flag, connector, configuration and on-disk format as a permanent test/maintenance obligation unless explicitly retired. Keep the one-command bootstrap and ordinary shell commands authoritative for humans and agents; wrappers may optimize presentation but cannot alter command results or be prerequisites for interpreting evidence.

### 4.6. CI became a bottleneck precisely when assurance mattered most

The [Oct 22 critical-path report](https://github.com/trickle-labs/rockstream/blob/f550c8f0094903d8989447ec09dfc3859d168938/docs/ci-critical-path-2026-10.md) measured a successful-run median of 130.67 minutes including queues (eight successful PR runs). A queue-free dependency-only replay estimated 95.92 → 69.70 minutes, a 27.3% reduction, **not** an observed hosted improvement. The report moved non-dependent work out of critical paths and preserved important scale assertions with smaller PR cases plus expensive scheduled cases.

By Nov 25, [#458](https://github.com/trickle-labs/rockstream/issues/458) reported a 200-PR-triggered-run convenience sample: 68 CI runs, 15 successful, four failed, 35 canceled, 14 pending/queued; median successful turnaround 386 minutes (134–899 minutes), five full job lists with 534–580 occupied runner-minutes per run. In [#447's CI](https://github.com/trickle-labs/rockstream/actions/runs/45515230197), an eight-second selection job and a five-second final gate reportedly waited 72 and 71 minutes respectively. A brittle doc check in [#448's run](https://github.com/trickle-labs/rockstream/actions/runs/45445288446) failed after about 434 minutes. This review confirmed the referenced runs' success/failure and creation/update timestamps in the Actions API; the detailed job timing and aggregate samples are issue-reported. The samples are not controlled comparable experiments; do not infer a precise deterioration factor or billing cost. [#460](https://github.com/trickle-labs/rockstream/issues/460) explicitly says the actual limiting runner quota is unverified. [#459](https://github.com/trickle-labs/rockstream/pull/459) proposes preflight and timing improvements; [#465](https://github.com/trickle-labs/rockstream/pull/465) proposes reducing brittle model-path coupling. These were open at the snapshot, not measured fixes.

**Root cause inference:** as real safety and qualification work expanded, monolithic/repeated builds, required-job fan-out, queue contention, and costly late failures combined. Adding more parallel agents or jobs without capacity control risks producing more canceled work, not more accepted changes. The corrective work was worthwhile; it was placed too late and too frequently on expensive critical paths.

**Better approach:** adopt [Rockstream 2's development workflow](../design/development-workflow.md) from the first executable commit. Start with low-cost deterministic preflight and focused local replay; build once per compatible profile, shard by measured time, isolate deep verification capacity, cancel obsolete PR work, and test the final gate against missing/skipped/canceled jobs. Select risk-based extended tests with conservative transitive dependencies and independent checker tests. Run scheduled exploration, deep soaks and cloud measurements with separate capacity and bounded backlog; required safety evidence is never silently demoted. Measure trigger-to-green including queue, time-to-first-actionable-failure, occupied minutes, canceled work, evidence age, and safe accepted changes. G0's proposed <5-minute median/<10-minute P95 ordinary PR CI and 1–10 second warm feedback are objectives, not demonstrated results or grounds for bypassing safety. Start with a cheap docs-only check and a small executable kernel before expanding.

### 6.1. Review questions for every implementation issue

Use the existing issue and PR templates; the following prompts are not a new form or documentation burden.

- **Reachability:** which ordinary caller actually uses the change? What observation would show the wrong implementation ran?
- **Safety:** which invariant and failure action does it preserve? What happens on timeout, ambiguous durable outcome, cancellation, stale authority, restart, and resource exhaustion where applicable?
- **Evidence:** what is the smallest independent, failing-before regression with complete expected results? Can the check itself be fooled? Which exact case/feature/backend ran?
- **Work:** what bounds processing, state, memory and I/O; what grows with unrelated data or consumer retention? Is the bound enforced before allocation/work?
- **Scope:** what is deliberately unsupported, and how does the executable reject it? Is there a new permanent compatibility or maintenance commitment?
- **Integration:** which gate and canonical document own this promise? What remains unqualified after merge? Is a narrower safe slice possible?

For low-risk changes this can be a few lines. A high-risk change requires the corresponding detailed contract and evidence, independent review and maintainer authorization. A bigger generated report is not a substitute for a test or a decision.

### 6.2. Measure engineering progress rather than activity

Use a small weekly scorecard computed from normal issue, PR and CI records, not manually assembled proof theater. Start collecting in G0, segment by risk, and calibrate goals from actual data:

| Measure | Decision it enables |
| --- | --- |
| Ready issue → accepted integrated safe change, median/P95; review and decision wait | Whether the bottleneck is issue scope, dependency, approval or implementation. Do not count abandoned PRs as throughput. |
| CI trigger-to-green and first actionable failure; runnable queue vs execution; occupied minutes and obsolete/canceled work | Whether to improve fast preflight, build graph, selection or capacity. Preserve exact test coverage and candidate identity. |
| Rework, reverts and escaped defects by invariant; replayable regression completion | Where to invest in contracts, independent oracles, fault injection, or smaller integration boundaries. |
| Verification backlog age and coverage of supported contracts, not raw test count | Whether promotion risk is accumulating even while PRs merge. Unknown/missing evidence is explicit. |
| Agent/CI/cloud cost per accepted change and per qualification campaign | Whether to adjust WIP, simplify harnesses, change runtime strategy or add capacity. Include failed/abandoned work; do not infer spend from PR count. |
| Complete-path latency, work amplification, resource bounds and cost per qualified workload | Whether the product improves on the donor and meets the frozen profile rather than a synthetic microbenchmark. |

No target should incentivize concealing failures, avoiding difficult issues, or weakening gates. A slow high-risk PR can be the correct outcome. Track and resolve the bottleneck rather than silently excluding it from the metrics.

## 7. Final perspective

The central recommendation is to preserve Rockstream's accumulated **failure knowledge**, while changing the order in which product value, correctness evidence, and implementation breadth are earned. A narrow, executable, independently observed path is worth more than many nominally complete modules. A small test that catches an actual safety violation is worth more than an impressive inventory of checks that might not execute. A scoped, qualified claim is worth more than an ambitious release label.

Rockstream 2 should be able to show, early and repeatedly: this is the actual deployed path; these are the promised cuts and complete results; these are the exact failures delivered and tolerated; these are the measured resource and cost boundaries; and this is what remains unsupported. Keep that evidence fast enough to use on every appropriate change. If the successor retains this discipline, the old implementation's most expensive lessons become an advantage rather than technical debt carried into a new architecture.
