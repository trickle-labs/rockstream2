### Primitive guarantees and Rockstream responsibilities

**SlateDB:** a durable checkpoint names a manifest and protects its reachable files. An in-process `DbSnapshot` is not that durable protection. A reader pinned to a supplied checkpoint differs from a reader following newer state; the latter must not be substituted for an exact published version. Clones start from checkpointed state while sharing source files. These are useful building blocks, but they do not establish Rockstream's logical cut, cross-arrangement atomicity, or retained per-epoch output history. The arrangement layer must preserve those semantics through compaction and recovery. See the [checkpoint documentation](https://slatedb.io/docs/design/checkpoints/) and [versioned reader API](https://docs.rs/slatedb/0.16.0/slatedb/struct.DbReader.html).

The [clone design](https://slatedb.io/docs/design/clones/) also describes referenced WAL SST copying and external checkpoint dependencies; administrative creation does not flush the live source writer. Qualify exact durable source selection and full clone/cleanup cost. An explicit-checkpoint reader does not refresh or delete its caller-managed checkpoint. Zero-pin-write follow-latest behavior cannot substitute for GC-safe Rockstream protection. Reader-group amortization and manifest-selected attempt namespaces are proposed compositions that require their own models and exact-version conformance tests.

**Transactional objects:** `slatedb-txn-obj` exposes version-conditional updates of one object through a supplied storage protocol, with an optional fencing wrapper. Its object-store protocol represents a sequence of numbered versions; reuse must not assume that its implementation is an overwrite of a single key. Rockstream proposes one logical metadata root pointing to immutable metadata nodes. Admission, ownership, publication, pin eligibility and reclamation conditions that must change atomically belong to that root transition. The library does not supply the application state machine, a cross-object transaction, a wall-clock lease, or Rockstream's retry/GC proof. See the [0.17.0 API](https://docs.rs/slatedb-txn-obj/0.17.0/slatedb_txn_obj/).

**Object storage:** S3 documents strong consistency and atomic updates to an individual key. `If-Match` checks the current ETag; `If-None-Match` supports conditional creation. There is no implied multi-key transaction. Rockstream must qualify the selected client's actual conditional operations, read/list behavior, conflict and unknown-outcome handling, durable retention, and initialization rules. An S3-compatible API name alone is insufficient. A metadata root CAS is a design built on these primitives, not evidence that a particular backend or deployment already meets the full contract. See [S3 consistency](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html#ConsistencyModel) and [conditional writes](https://docs.aws.amazon.com/AmazonS3/latest/userguide/conditional-writes.html).

**Embedded Raft:** OpenRaft provides a consensus implementation, while the application implements storage and network interfaces. Its restart/data-loss guidance assumes preservation of the necessary durable log, vote, snapshot and membership state. A majority-based group cannot commit new decisions while every voter is asleep. Consequently, embedding a library removes a separately operated service but does not itself deliver disposable authority state or automatic wake-up. It remains an evidence-triggered alternative to the proposed object-store metadata kernel, with its own recovery and operating-cost qualification. See the [integration guide](https://docs.rs/openraft/0.9.21/openraft/docs/getting_started/index.html) and [FAQ](https://docs.rs/openraft/0.9.21/openraft/docs/faq/index.html).

The versions above identify documentation inspected for this design; they are not a compatible dependency lockfile or a recommendation to use these exact releases. G0 must select and pin a mutually compatible set. No external etcd, ZooKeeper, Redis or PostgreSQL catalog service is required by the proposed deployment contract.

## 4. Evidence classifications for future work

Use **Observed implementation** for a pinned code path actually inspected; **Declared support** for a versioned capability contract; **Research precedent** for a cited result; **Proposed requirement** for this repository's design; and **Measured result** only for a reproducible executed bundle. A unit fixture, mock UI number, unexecuted test specification or model with unstated bounds must never be labelled a measured result.

When a source changes, preserve the qualified dependency revision in the evidence bundle. When a design inference changes, update the ADR and affected contracts. Keep primary sources close to factual claims; keep this index as a navigation aid rather than a substitute for local reasoning.
